# 真实踩雷与生产检查

[English](../en/docs/production-pitfalls.md)

> 核对日期：**2026-10-13**。本页只收录能由厂商官方文档或仓库脱敏实测记录支持的问题；跨厂商结论会明确写出适用范围，不把“OpenAI-compatible”误解为参数语义完全一致。[来源与核验规则](来源与核验规则.md)

## 1. 最大的坑：思考可能吃掉输出预算

### 现象

- `reasoning_content` 很长，最终 `content` 很短、为空或半句话结束。
- HTTP 状态仍是 200，代码只判断请求成功，因此把残缺结果继续交给下游。
- `finish_reason` 是 `length`，而不是正常的 `stop`。

### 原因不是所有厂商都一样

Kimi 明确规定：`reasoning_content` 与最终 `content` 的 token 数之和不能超过 `max_tokens`。官方还建议 K2.6/K2.7 Code 做多步工具调用时设置 `max_tokens >= 16000`，以免思考或回答不完整。[Kimi 思考模型](https://platform.kimi.com/docs/guide/use-thinking-models)

阿里云百炼当前同时提供 `max_tokens` 和 `max_completion_tokens`：`max_completion_tokens` 限制“思维链 + 回答”的完整输出；`max_tokens` 的含义会随模型变化，部分模型限制两者之和，其他模型只限制回答。因此不能写一个通用封装，想当然地认为所有模型的 `max_tokens` 都有同一含义。[百炼 Chat Completions 参数](https://help.aliyun.com/zh/model-studio/qwen-api-via-openai-chat-completions/)

具体到本仓库收录的 `qwen-flash`：官方当前把它归入 `max_tokens` 只限制正文的范围；千问 Flash 的 `max_completion_tokens` 支持范围从 Qwen3.5-Flash 起，不能直接替换到旧 `qwen-flash` 型号。[百炼 Chat Completions 参数](https://help.aliyun.com/zh/model-studio/qwen-api-via-openai-chat-completions/) 生成器只采用当前型号卡片登记的参数。[模型卡片](../skills/model-manual/references/models/qwen-flash.json)

DeepSeek 把思考 token 暴露为 `usage.completion_tokens_details.reasoning_tokens`，并用 `finish_reason="length"` 表示达到生成上限；这两个字段应一起进入监控。[DeepSeek Chat Completions API](https://api-docs.deepseek.com/api/create-chat-completion/)

MiniMax M2.7（补充核对：2026-10-14）的思考不能关闭，`reasoning_split` 只影响思考放在哪个输出字段；`disabled` 请求不等于停止思考。官方 SDK 对旧 `max_tokens` 明确说明思考也计入，但当前 `max_completion_tokens` 的 M2.7 字段说明未明确同样的计入规则，本项目标为待确认，不按其他型号推断。[MiniMax Chat 参数](https://platform.minimax.cn/docs/api-reference/text-chat-openai) · [MiniMax SDK 思考与参数](https://platform.minimax.cn/docs/api-reference/text-openai-api)

### 修复

项目建议：每次都检查 `finish_reason`、正文是否为空和 token 用量；思考任务不要沿用非思考任务的 128/256 token 小上限。参数名和预算语义必须从当前模型说明书读取，而不是按厂商或 SDK 猜测。[来源与核验规则](来源与核验规则.md)

```python
choice = response.choices[0]
content = choice.message.content or ""

if choice.finish_reason == "length":
    raise RuntimeError("模型输出达到上限；回答可能已被截断")
if not content.strip():
    raise RuntimeError("正文为空；检查思考 token 是否耗尽输出预算")

usage = response.usage
details = getattr(usage, "completion_tokens_details", None)
reasoning_tokens = getattr(details, "reasoning_tokens", None)
print({
    "completion_tokens": getattr(usage, "completion_tokens", None),
    "reasoning_tokens": reasoning_tokens,
    "finish_reason": choice.finish_reason,
})
```

不要把“重新请求”作为唯一修复：如果预算仍然过小，重试可能继续得到截断结果。项目建议先核对正确的输出参数与预算；降低推理强度或关闭思考仅适用于明确支持的型号，再做有限次数重试。[来源与核验规则](来源与核验规则.md)

## 2. 只看 HTTP 200，不看 `finish_reason`

DeepSeek 文档列出的结束原因包括 `stop`、`length`、`content_filter`、`tool_calls`、`insufficient_system_resource` 和 `aborted`；文档把 `stop` 定义为自然停止或命中停止词，把 `tool_calls` 定义为模型调用了工具。[DeepSeek Chat Completions API](https://api-docs.deepseek.com/api/create-chat-completion/)

MiniMax 原生接口还返回 `base_resp.status_code` 业务状态；项目示例同时检查业务状态、结束原因和非空最终正文。不能只用 HTTP 成功判断，或把仅有 `<think>` 的内容当成最终答案。[原生响应字段](https://platform.minimax.cn/docs/api-reference/text-post) · [M2.7 示例](../models/minimax/MiniMax-M2.7/examples/sources.json)

项目建议：在解析 JSON、写数据库、执行代码或展示最终答案之前，先按结束原因分支处理。[来源与核验规则](来源与核验规则.md)

```python
reason = response.choices[0].finish_reason
if reason == "tool_calls":
    handle_tool_calls(response.choices[0].message.tool_calls)
elif reason == "length":
    raise RuntimeError("结果被截断，禁止当作完整答案使用")
elif reason != "stop":
    raise RuntimeError(f"模型未正常结束：{reason}")
```

## 3. JSON Mode 不等于业务数据一定正确

DeepSeek 官方要求：启用 `response_format={"type":"json_object"}` 时，提示词也必须明确要求 JSON；否则模型可能持续输出空白直到耗尽 token，看起来像请求卡住。即便是 JSON Mode，`finish_reason="length"` 时内容仍可能被截断。[DeepSeek Chat Completions API](https://api-docs.deepseek.com/api/create-chat-completion/) · [DeepSeek JSON Output](https://api-docs.deepseek.com/guides/json_mode/)

百炼同样要求 `json_object` 模式的提示词明确包含 JSON 指令；`json_schema` 与 `json_object` 的模型支持范围不同。[百炼 Chat Completions 参数](https://help.aliyun.com/zh/model-studio/qwen-api-via-openai-chat-completions/) · [百炼结构化输出](https://help.aliyun.com/zh/model-studio/qwen-structured-output)

项目建议：结构化结果至少经过“结束原因检查 → `json.loads` → Schema/业务规则校验”三层；模型给出的合法 JSON 仍可能包含错误枚举、缺失业务关系或虚构值。[来源与核验规则](来源与核验规则.md)

## 4. Tool Calling 返回了 JSON，不代表可以直接执行

DeepSeek 接口文档明确提醒：模型生成的工具参数不保证是合法 JSON，也可能虚构函数 Schema 中没有的参数，调用真实函数前必须验证。[DeepSeek Chat Completions API](https://api-docs.deepseek.com/api/create-chat-completion/)

项目建议：工具名使用 allowlist；参数先解析再做 JSON Schema 和业务权限校验；写操作增加幂等键与人工确认；工具循环设置最大轮次。这些是本项目的安全约定，不是厂商对模型正确性的承诺。[来源与核验规则](来源与核验规则.md)

```python
allowed_tools = {"get_weather": get_weather}
call = message.tool_calls[0]

if call.function.name not in allowed_tools:
    raise PermissionError("模型请求了未授权工具")

arguments = json.loads(call.function.arguments)
validate_weather_arguments(arguments)  # 类型、枚举、长度和权限
result = allowed_tools[call.function.name](**arguments)
```

## 5. 工具循环里丢掉思考字段，下一轮可能报错或退化

Kimi 要求 K2.6/K2.7 Code 在一次多步工具调用中保留全部 `reasoning_content` 并随请求回传；启用 K2.6 的 `thinking.keep="all"` 时，也要完整保留历史 assistant 消息。[Kimi 思考模型](https://platform.kimi.com/docs/guide/use-thinking-models)

DeepSeek 在带 `tools` 的思考模式中要求完整回传此前的 `reasoning_content`；缺失时接口会返回 400。[DeepSeek Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode/)

因此不要只构造 `{"role":"assistant","content": message.content}`。项目建议直接保存 SDK 返回的完整 assistant message，再附加工具结果；但持久化前应按业务数据政策处理可能包含敏感信息的思考内容。[来源与核验规则](来源与核验规则.md)

## 6. 流式 chunk 不保证每块都有正文

DeepSeek 的流式用量位于结束前最后一个 chunk；该 chunk 不再携带新正文，并带有非空 `finish_reason`。开启思考时，还会先收到 `delta.reasoning_content`，之后才是 `delta.content`。[DeepSeek Chat Completions API](https://api-docs.deepseek.com/api/create-chat-completion/) · [DeepSeek Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode/)

Kimi 也说明流式场景中 `reasoning_content` 先于 `content`，而部分 OpenAI SDK 类型没有静态声明该扩展字段，需要用 `getattr`/`hasattr` 访问。[Kimi 思考模型](https://platform.kimi.com/docs/guide/use-thinking-models)

项目建议：不要写 `chunk.choices[0].delta.content` 后直接拼接；先检查 `choices`，再分别读取思考、正文、结束原因与 usage。[来源与核验规则](来源与核验规则.md)

```python
reasoning_parts = []
content_parts = []
finish_reason = None
final_usage = None

for chunk in stream:
    if getattr(chunk, "usage", None):
        final_usage = chunk.usage
    if not chunk.choices:
        continue
    delta = chunk.choices[0].delta
    reasoning_parts.append(getattr(delta, "reasoning_content", None) or "")
    content_parts.append(delta.content or "")
    if chunk.choices[0].finish_reason:
        finish_reason = chunk.choices[0].finish_reason

if finish_reason != "stop":
    raise RuntimeError(f"流式结果未完整结束：{finish_reason}")
if not "".join(content_parts).strip():
    raise RuntimeError("流式正文为空")
```

完整可运行的保护代码见[流式示例](../models/kimi/kimi-k2.6/examples/02_streaming.py)。本仓库离线测试用模拟截断、空用量块和工具响应检查实际代码路径，在线验证报告另行记录真实请求结果。[验证与复现](验证与复现.md)

## 7. `extra_body` 放错位置，参数可能根本没生效

百炼文档规定，使用 OpenAI Python SDK 时，`enable_thinking`、`thinking_budget` 等非 OpenAI 标准字段应放入 `extra_body`；直接用 HTTP 请求时则放在 JSON 请求体顶层。[百炼 Chat Completions 参数](https://help.aliyun.com/zh/model-studio/qwen-api-via-openai-chat-completions/)

Kimi 与 DeepSeek 的思考开关同样属于厂商扩展字段，本仓库 Python 示例通过 `extra_body` 传入。[Kimi 思考模型](https://platform.kimi.com/docs/guide/use-thinking-models) · [DeepSeek Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode/)

项目建议：不要仅凭“请求没有报错”判断参数生效；同时检查响应是否出现 `reasoning_content`，并用仓库验证脚本分别测试开启和关闭两条路径。[Kimi 验证记录](../models/kimi/kimi-k2.6/verification/2026-10-13.json) · [DeepSeek 验证记录](../models/deepseek/deepseek-flash/verification/2026-10-13.json)

## 8. 429 不等于 Key 错了，也不等于模型永久不可用

本仓库在 2026-10-13 调用 `glm-4.7-flash` 时，请求到达服务后分别收到 HTTP 429、业务码 `1302`（账户速率限制）和 `1305`（模型当前访问量过大）；因此验证报告记录为 `rate_limited`，没有写成认证失败或能力不支持。[智谱实测记录](../models/zhipu/glm-4.7-flash/verification/2026-10-13.json)

项目建议：先按 HTTP 状态码和厂商业务码分类；429 使用带随机抖动的指数退避并设置最大次数，401/403 检查密钥和权限，400 修正请求体。不要对所有错误无差别重试。[来源与核验规则](来源与核验规则.md)

## 9. “模型还能调用”不等于“适合新项目继续绑定”

火山方舟当前把 `doubao-seed-2-1-pro-260628` 放在往期模型区域，而本仓库 2026-10-13 的七项调用仍全部成功。[火山方舟模型列表](https://docs.volcengine.com/docs/ark/model-list?lang=zh) · [豆包实测记录](../models/doubao/doubao-seed-2-1-pro-260628/verification/2026-10-13.json)

项目建议：Model ID 必须配置化；上线前同时检查官方生命周期和真实探活，不因一次成功就忽略迁移，也不因“往期”两个字就擅自判定接口已经下线。[来源与核验规则](来源与核验规则.md)

## 10. 思考历史既占上下文，也会增加费用

Kimi 明确说明 `reasoning_content` 会计入 token 消耗；开启保留式思考后，历史思考会持续占用上下文并计费。[Kimi 思考模型](https://platform.kimi.com/docs/guide/use-thinking-models)

项目建议：只在确实需要延续推理的多轮任务保留思考；普通聊天、检索问答和简单抽取优先关闭思考或不保留历史思考。价格计算必须使用响应中的实际 usage，并在使用前复核各厂商[官方价格入口](04-免费额度与省钱攻略.md)。

## 上线前最小检查表

以下是本项目根据上述官方行为整理的检查项；它属于项目建议。[来源与核验规则](来源与核验规则.md)

- Key 只从环境变量读取，日志不输出完整 Key。
- 固定并记录 Model ID、Base URL、SDK 版本和核验日期。
- 分别实测普通、流式、思考开/关、JSON、工具调用；多模态模型再测图片。
- 检查 `finish_reason`，拒绝把 `length` 当完整结果。
- 记录输入、输出和思考 token；为异常增长设置告警。
- JSON 做解析和 Schema 校验；工具参数做 allowlist、权限和幂等检查。
- 429、5xx、超时分别设置有限重试；写操作禁止盲目重放。
- 保存官方价格页与模型页链接，不把手抄价格当长期真源。
